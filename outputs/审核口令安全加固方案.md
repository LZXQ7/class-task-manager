# 审核体验入口 · 口令安全加固方案

> 背景：微信小程序**每个版本都要走人工审核**，而本小程序无账号密码体系（绑定靠「班级口令 → 名单选人 → 学号后 4 位」），审核员无法自行绑定。
> 故用一条「审核体验入口」旁路（`auth.reviewDemo`）：审核员在首页输入**审核口令**即一键进入 99 段演示超管，完整体验主要功能。
> 用户问题（2026-10-12）：「这个审核用的口令怎么才能安全一点」——下面评估现状风险并给出可落地加固方案。

---

## 一、现状（1.0.6.3 / 1.0.6.4 的 `reviewDemo` 机制）

### 已经做对的（保留）
1. **口令存 DB 不进前端包**：`class.review_demo_code`，代码随包被反解也拿不到；前端只拿布尔位 `reviewDemo` 决定要不要渲染入口。
2. **口令只填 mp 后台「审核备注」**，不随代码分发。
3. **恒定时间比较 `safeEqual`** → 防时序侧信道爆破。
4. **失败计数 + 30 分钟锁**（`recordFail` / `lockFor`，对应 `BIND_MAX_FAIL` / `BIND_LOCK_MIN`）→ 防暴力穷举。
5. **绑定目标锁死 99 段测试超管**（`role='ADMIN' AND is_super=1`），绝不顶掉真人 → 爆出口令也只得到演示身份。
6. **开关 `review_demo_on` 默认关**，审核后一条 `UPDATE` 即关，不必重部署。

### 仍脆弱的点（风险）
| # | 风险 | 说明 |
|---|---|---|
| A | **单因素 + 无有效期** | 口令一旦设下、只要 `review_demo_on=1` 就一直有效；审核通过后若忘了关，或关了但口令没轮换，下次提审直接复用旧口令 = 长期暴露面。口令本身无 TTL，泄露即永久可用直到手动关。 |
| B | **口令明文存 DB** | `review_demo_code` 是明文。虽只有超管能读，但 DB 备份 / 脱敏导出 / 内部误操作都可能泄露明文口令。 |
| C | **口令易复用、长期不变** | 每次提审图省事复用同一口令（如 `LXQ-L3SS-CGHQ-DUWG-T5`），一旦该口令在任何渠道泄露，后续每次提审都裸奔。 |
| D | **演示身份是「完整超管」** | 审核员拿到的是 `is_super=1` 全权限超管。口令泄露 ⇒ 攻击者可做任意超管操作（改成员、发通知、动配置）。审核其实只需「能完整体验主要功能」。 |
| E | **无审计留痕** | `reviewDemo` 成功绑定只 `console.log`，没写 `admin_audit_log`，无法事后发现「口令被外人用过」。 |
| F | **演示会话不过期** | 绑定后演示超管的 `openid` 一直绑着（除非关闭时 `UPDATE member SET openid=NULL`），长期驻留。 |

---

## 二、加固方案（分三档，按需取用）

### 🟢 轻量档（低成本、立刻能做；建议至少做这档）
1. **强制轮换 + 自动过期**
   - 每次提审前生成**全新高熵口令**，绝不复用上一版。
   - `class` 加 `review_demo_expire` 字段（DATETIME）；开入口时设 `NOW()+N天`（如 7 天）。
   - `reviewDemoRow` 的查询条件加 `(review_demo_expire IS NULL OR review_demo_expire > NOW())`；过期即视为未开放 → **即使忘了关也自动失效（自愈）**。
   - 关闭脚本一并清 `review_demo_code` / `review_demo_expire`。
2. **口令存哈希不存明文**
   - `review_demo_code` → `review_demo_code_hash`，用 scrypt / bcrypt（与 `admin-web` 同款）。
   - 开入口时用脚本生成哈希写入；比较走 `safeEqual(哈希(输入), 存储哈希)` 或 scrypt 的 verify。DB 泄露也拿不到明文口令。

### 🟡 中量档（推荐，覆盖 A/B/C/E）
在轻量档基础上加：
3. **审计留痕**：`reviewDemo` 成功 / 失败时均写 `admin_audit_log`（action=`review.demo.login`，记 openid / 时间 / 是否演示）。事后可查有无异常使用。
4. **限定次数（可选）**：口令成功后 N 次（如 5 次）即作废，强制每次提审换新；或「首次成功绑定后自动关入口」（但审核员可能需多次进入，给次数上限更稳）。

### 🔴 重量档（缩小权限面，覆盖 D/F）
5. **演示身份降权**：新建「审核体验角色」（`is_super=0` + 一组体验所需能力位），而非完整超管。审核员能看值日 / 课表 / 请假 / 排班，但改不了成员、发不了全局通知、动不了系统配置。**爆口令的爆炸半径从「全站超管」降到「只读体验账号」**。
   - 实现：新增 `member.role='REVIEW'` 或 `review_grant` 字段；`reviewDemo` 绑定到该受限身份而非 `is_super=1` 那行。
6. **演示会话 TTL**：绑定的演示 `openid` 加过期（如 24h 后由 cron 或下次进入时清），不长期驻留。

---

## 三、推荐落地组合

- **必做**：轻量档 ①（轮换 + 自动过期）+ ②（哈希存储）+ 中量档 ③（审计）。
  三项改动小——`class` 加 1~2 列 + `reviewDemo` handler 几行，立刻把「明文长期口令」变成「**哈希 + 限时 + 可溯源**」。
- **建议加**：重量档 ⑤（降权演示角色）—— 降低爆炸半径最关键，但需定义体验角色能力位，稍复杂。
- ⑥ 可暂缓。

## 四、实施成本与风险

- 改动集中在 `cloudfunctions/auth/index.js` 的 `reviewDemo` + `class` 表加列。
- 加列用 `ALTER TABLE class ADD COLUMN ...`（TDSQL 无 `IF NOT EXISTS`，**先查 `information_schema`** 再执行；备份表 `bak_class_*` 只 DELETE+INSERT、禁 DDL，与加列无关）。
- 部署：`auth` 函数需重部署（`fn code update`）+ 加列迁移；**前端无需改**（`reviewDemo` 布尔位照旧）。
- 每次提审流程变为：① 生成新口令 → ② 算哈希 + 设过期写入 `class` → ③ 填 mp 后台审核备注 → ④ 审核通过后关入口清字段。
