# 课表页加载慢 · 诊断结论（2026-10-15）

> 症状：用户报「课程表页加载特别慢」（版本 1.0.6.8）。
> 状态：**诊断已完成，修复未实施**（用户选择「先停在这里」）。线上已回滚到原状，功能正常。

---

## 一、结论速览

| 项 | 结论 |
|---|---|
| **主因** | 云函数包体积过大 ⇒ **冷启动慢**。`class` 本地源码 100 KB，线上 Code size **11.77 MB** |
| **次因** | 课表页首屏两个云函数**串行**（`class.list` → `course.allSessions`），全文无 `Promise.all` |
| **已排除** | **端上计算不是瓶颈**（实测 `sessionsOfWeek` = 0.058 ms/次）；网络往返仅 25–30 ms |

## 二、量化证据（全部实测，非推测）

### ① 端上计算：可忽略

`_dbg_room/perf-timetable-load.js`（Node 侧跑真代码，23 条课次）：

```
replaceSessions（落盘）              0.014 ms/次
sessionsOfWeek（第1周，过滤+排期）    0.058 ms/次
sessions()（读存储）                 0.000 ms/次
matchesWeeks("1-16")                0.000 ms/次
```

人类感知阈值约 100 ms 量级 ⇒ **端上计算不是问题**。

### ② 网络往返：正常

`_dbg_room/perf-cloud-latency.js`：热调用往返 **24–31 ms**（404 是路径不对，
这些云函数没开 HTTP 触发器，但网络基线已拿到）。

### ③ 云函数包体积：异常（真正的瓶颈）

`tcb fn detail` + `tcb fn code download` 实测：

| 函数 | 本地源码 | 线上 Code size | 下载后 node_modules |
|---|---|---|---|
| `class` | 100 KB | **11,769,839 B ≈ 11.2 MB** | **50 MB / 134 个包** |
| `course` | 807 KB（含 91 MB 本地 node_modules） | 16,519,178 B ≈ 15.8 MB | — |

`class/package.json` **只声明 2 个依赖**（`wx-server-sdk` 0.34 MB + `mysql2` 0.60 MB
= **0.94 MB**），线上却装了 134 个包。TOP 体积构成：

```
protobufjs                     14.36 MB   ← wx-server-sdk 的直接依赖（SDK 启动要用，不能删）
@typescript/typescript-win32-x64 27.05 MB  ← 🔴 TypeScript 的 Windows 平台二进制，云函数跑 Linux，纯死重
typescript                       2.38 MB   ← 🔴 类型声明
@types                           2.45 MB   ← 🔴 类型声明
source-map                       0.77 MB   ← 🔴 源码映射
```

**依赖来源链**（逐包追踪得出）：

```
class → wx-server-sdk → @cloudbase/node-sdk@2.9.1 → ts-node@8.10.2
                                                          ↓ peerDependencies（非 optional）
                                                     typescript ≥2.7
                                                          ↓
                                              @typescript/*（全平台二进制）
```

🔴 **真凶是 `ts-node` 的非可选 peer 声明** —— npm 7+ 会自动安装 peer，
于是把 TypeScript **全平台**二进制拖进包。

### ④ 缩包实验：有效（63 MB → 24 MB，运行时依赖仍可用）

`_dbg_room/pkg-shrink-experiment.js`：临时目录装全量 → 删类型声明/映射 → 探活。

```
全量安装          63.41 MB / 136 包
清理后            24.39 MB / 降 62%
探活：mysql2/promise ✅  wx-server-sdk ✅  mysql2 ✅
```

`scripts/slim-cloudfunction-pkg.js` 是它的产品化版本（含逐函数探活 + 失败即报）。

## 三、⚠️ 踩过的坑（必读，勿重试）

### ❌ 错误方案：`--install-dependency false`

**我试过并已在生产验证它是错的 —— 线上功能会坏，已紧急回滚。**

```bash
# ❌ 绝对不要用这个参数部署
tcb functions:deploy class --dir . --deployMode zip --install-dependency false
```

实测结果：

| 指标 | 表现 |
|---|---|
| `Code size` | 11.77 MB → **68.7 KB**（看着极好） |
| 实际上传的包 | **只有源码，没有 node_modules** |
| `fn code download` 复核 | `mysql2` ❌ 缺失、`wx-server-sdk` ❌ 缺失、`protobufjs` ❌ 缺失 |

该参数的语义是「**既不安装、也不上传依赖**」，不是「上传我已装好的依赖」。
压下去后线上函数启动即崩。

**回滚方式**（我实际执行过的）：

```bash
cd cloudfunctions/class
printf 'y\n\n\n\n' | node "$TCBJS" functions:deploy class -e "$ENV" --dir . --deployMode zip
# → Code size 回到 11.77MB，下载复核 mysql2/wx-server-sdk 均 ✅
```

💡 教训：**`--install-dependency false` 与「本地装好依赖再传」是两回事**。
CloudBase CLI 的 zip 模式不会把本地 `node_modules` 打进包。

### ❌ 其他已排除的思路

| 思路 | 实测结果 | 为什么不行 |
|---|---|---|
| `overrides: {"ts-node": "npm:..."}` | 安装直接失败 | 需要一个真存在的包名，不能用来「禁用」 |
| `npm install --omit=optional` | typescript 仍被装 | 它不是 optional，是**非可选 peer** |
| `npm install --legacy-peer-deps` | 63→34 MB ✅ | 有效，但**云端安装时我们控制不了这个参数** |

## 四、剩下的可行路径（均未实施）

### 路径 A：`npm-shrinkwrap` 固定依赖树（可继续做）

在函数目录提交 `npm-shrinkwrap.json`（npm-shrinkwrap 优先级高于 package-lock，
且**是云端安装时唯一可控的输入**），把 ts-node→typescript 那条链剪掉。
预期 `class` 从 11.77 MB 降到约 4 MB。

- 成本：要重新部署 12 个函数，**每个部署后都要验证接口**（本次教训就是「验证必须做」）。
- 风险：中。剪错依赖树会让函数启动失败，但症状立即可见（部署后调用即报错）。

### 路径 B：请求并行化（低风险，收益较小）

课表页首屏 `class.list` → `course.allSessions` 改成 `Promise.all`，
并把班级配置（termStart / periodTime）提前预取。

- 收益：热调用下从 ~60 ms 降到 ~30 ms。
- 局限：**解决不了冷启动**（首次进入 / 部署后首次仍是秒级等待）。

### 路径 C：先用真机面板定位（建议的下一步）

用微信开发者工具的 **Performance 面板 / 真机调试 → 性能** 量一次，
把时间花在哪一段（网络 / 冷启动 / 渲染）确认清楚，再决定投哪个路径。

- 理由：目前「冷启动是主因」是由 `Code size 11.7MB` +「端上计算可忽略」
  **推断**的，尚缺真机上的直接证据。

## 五、课表页加载链路（供优化参考）

```
onShow
 └─ _afterAuth()
     └─ _loadTimetableClasses()      → api.classList        （只为了拿 termStart / periodTime）
         └─ _afterClassPicked()
             └─ _syncFromCloud()     → api.courseAllSessions
                 └─ load()           → 纯本地渲染（0.058ms，非瓶颈）
             └─ _loadPersonal()      → api.electiveList
```

- 🔴 全页**无 `Promise.all`** ⇒ 请求严格串行。
- `_booted && sameClass && sameIdentity` 时走本地即时渲染 + 后台静默同步
  （这条路径已经优化过，不是问题所在）。
