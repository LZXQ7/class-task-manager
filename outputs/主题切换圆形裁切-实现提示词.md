# 主题切换 · 圆形裁切揭示 —— 实现提示词

> 可直接整段复制交给 AI 执行。术语已按 Animation Vocabulary 校准，落地约束基于本项目实测现状。

---

## 目标

为微信小程序实现「跟随系统深色模式」。**明暗切换的过渡必须是圆形裁切揭示，不是整屏淡入。**

## 一、动效规格（术语基线）

核心词：**circular clip-path reveal** · **origin-aware animation** · **reveal**

1. **两层真实存在，不做 Crossfade。**
   底层是当前主题的完整页面，上层是新主题的完整页面。两层同时在视图树里、内容各自独立渲染。
   切换时只是「揭开」上层，不是让一个元素淡出、另一个淡入。

2. **只裁不缩。**
   上层用 `clip-path: circle()` 揭示。**禁止用 Scale 模拟** —— 缩放会让文字和图形在边缘扫过时发生形变。
   验收标准：圆边扫过处，被覆盖的那层文字**一个像素都不变形**。

3. **圆心即触点（origin-aware）。**
   圆心取触发切换的那一点，**不是元素自身中心**（CSS 默认是自身中心，必须显式覆盖）。
   这是 *Origin-aware animation*：元素从它的触发点长出来。

4. **半径 = 触点到底部四个角中最远那个角的距离。**
   `r = max( √(dx² + dy²) )` —— 四个角全算一遍，取最大值。
   这样圆长到 r 时**刚好铺满全屏**，不多不少，不会出现「圆涨满了但角上还漏一条边」。

5. **缓动用 Ease-out**（起快收慢，响应式交互的默认）。
   避免 **Ease-in**，对用户触发的动效会显得拖沓。想要更有生气可用 **Asymmetric easing**。

6. **尊重 Reduced motion。**
   `prefers-reduced-motion: reduce` 时降级为直接切换。

7. **性能。**
   `clip-path` 每帧触发 **paint**、走不了 **Compositing**，低端机有 **Jank** 风险。
   动画期间给上层加 **will-change: clip-path**，并确保不触发 **Layout thrashing**。

## 二、主题来源

- 读系统偏好，**不猜用户意图**。与 *Reduced motion* 同族思路：系统说什么就是什么。
- 手机深色 → 微信深色 → 小程序默认深色；浅色同理。
- **首屏必须无闪烁**：在渲染前就定好主题，不能先渲染浅色再跳深色。
- 系统主题在运行中变更时，同样走上面这套圆形揭示。

## 三、关键设计张力（先说清楚，别踩）

**主题跟随系统 = 触发源是系统事件，不是手指。**

`wx.onThemeChange` 是系统/微信触发的，此时**根本没有触点**。所以「圆心 = 手指按下的那一点」要分两种情况：

| 触发源 | 圆心取哪 |
|---|---|
| 用户点了小程序内的主题切换按钮 | 该次点击的触点 |
| 系统/微信主题变更（`wx.onThemeChange`） | 屏幕中心，或**全局记录的最后一次触点位置**作为近似 |

⚠️ 另外：**完全跟随系统时用 `@media (prefers-color-scheme: dark)` 就够了 —— 但媒体查询是瞬时翻转的，无法参与动画。**
所以主题必须是 **JS 状态 + class 驱动**，媒体查询只能当兜底。

## 四、本项目的落地约束（已实测）

1. `miniprogram/app.json` 当前 `"renderer": "webview"` → **`clip-path` 可用**；
   但小程序**没有 View Transitions API**，这套必须手写，不能吃浏览器内置的圆形揭示。

2. `app.json` 当前**没有任何深色模式配置**（无 `darkmode`、无 `themeLocation`、无 `theme.json`），
   全仓搜 `onThemeChange` / `prefers-color-scheme` 零命中 —— 从零新增。
   ⚠️ 别被 `"backgroundTextStyle": "dark"` 误导，那与深色模式无关。

3. **设计令牌已全部集中在 `miniprogram/app.wxss` 的 `page {}` 块**，约 40 个：
   - 颜色类（**需要深色版**）：`--bg-page` `--bg-card` `--bg-fill` `--bg-mask` / `--text-1..4` `--text-white` /
     `--line-1` `--line-2` / `--brand` `--brand-press` `--brand-disable` `--brand-light` /
     `--success` `--success-bg` `--warning` `--warning-bg` `--danger` `--danger-bg` `--purple` `--purple-bg` /
     `--shadow-1` `--shadow-2` / `--glass-bg` `--glass-bg-strong` `--glass-edge` `--glass-shadow` `--glass-highlight`
   - 尺寸类（**不需要深色版，别复制**）：`--r-sm/md/lg/pill` `--nav-h` `--tab-h` `--glass-blur`
   两套主题不要用 `page {}` 覆盖，而是定义**作用域化的 class**（如 `.t-light` / `.t-dark`）各自声明整套令牌 ——
   因为两层要同时以不同主题存在，全局覆盖做不到这件事。

4. **原生 UI 只剩一处**：`navigationStyle: "custom"` + `tabBar.custom: true`，
   所以导航栏和 tabBar **都是自绘 WXSS**，跟着 class 走即可。
   只有 **`window.backgroundColor` / `backgroundTextStyle`**（下拉回弹露出的底色）是原生的，CSS 够不到
   → 这一处必须走 `"darkmode": true` + `themeLocation: "theme.json"` + `"@bgColor"` 变量引用。
   （`theme.json` 只允许管原生属性：navigationBarBackgroundColor / navigationBarTextStyle /
   backgroundColor / backgroundTextStyle / backgroundColorTop / backgroundColorBottom，以及 tabBar 的
   color / selectedColor / backgroundColor / borderStyle / iconPath / selectedIconPath。）

5. 项目已有 15 个自定义组件（`components/`），把页面内容抽成组件、渲染两份的成本可控。

## 五、「两份渲染」的取舍

只要严格满足「两套页面都真实存在」，就必须渲染两份。两条路：

- **方案 A（严格符合要求）**：页面内容抽成一个自定义组件，在页面里渲染两次 ——
  一份带浅色令牌、一份带深色令牌；上层用 `clip-path` 揭示。
  代价：节点数翻倍。本项目页面体量不大，可接受。
- **方案 B（省一半节点，但不达标）**：只揭示一层纯色背景圆，文字靠 CSS transition 同步变色。
  问题：文字不是「被圆扫出来」的，圆边扫过时会看到颜色**同时**在变，**不满足验收标准**。

选 A。如果实施后发现某页节点过多导致卡顿，再针对该页单独降级，而不是整体退回 B。

## 六、术语黑名单

写错就会做错，务必避免：

- ✗ **Ripple** —— 那是点击反馈：圆是装饰、会消失、外面页面照旧。
  这里圆是**裁切开口**：结束状态要铺满全屏并**留在那儿**。
  判据就是「两套页面都真实存在」这一句 —— 有这句话就不是 Ripple。
- ✗ **Crossfade** —— 整屏淡入淡出，明确不要。
- ✗ **Scale** —— 缩放必然导致内容变形，明确不要。

## 七、验收判据

1. 深浅两套页面在切换过程中**同时存在于视图树**。
2. 圆边扫过时，**文字零形变**（放大截图逐像素比对圆边两侧的字）。
3. 圆心落在触发点（主动点击时）。
4. 圆铺满全屏时，**四个角全部覆盖**，无残留边条。
5. 首屏加载**无浅色闪烁**。
6. `prefers-reduced-motion: reduce` 下无揭示动画。
7. 切换过程中不出现明显掉帧。
